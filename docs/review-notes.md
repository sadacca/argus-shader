# v0.1 → v0.2 Review Notes

Technical review of the v0.1 requirements against the libretro slang shader spec and the stated
ARM target hardware (Adreno 6xx/7xx). Findings are ordered by severity. Four are blocking — the
plan as written could not be built. The rest are optimizations and process fixes.

---

## Blocking: specified behavior that does not exist

### B1 — FR9's dual-axis preset composition is not expressible

**v0.1 said:** the system and genre profiles "combine multiplicatively via preset parameter sets"
and map onto RetroArch's preset specificity hierarchy.

**Problem:** RetroArch's `#reference` directive permits exactly one level of indirection —
*references to references are not supported*. A chain of `root → genesis.slangp →
genesis-fast-action.slangp` cannot be expressed, and no preset-level mechanism merges two
orthogonal parameter sets at load time. The specificity hierarchy (global → core → content-dir →
per-game) selects *one* preset; it does not compose two.

**Change:** the cross-product is resolved at build time. Each (system × genre) pair is emitted as
a flat `.slangp` with a single `#reference` to the root preset plus merged parameters from both
axes, generated by a script from two profile tables. ~20 files, never hand-edited.

**Consequence:** the preset generator becomes a real deliverable with its own tickets, not an
afterthought. It also has to exist before the console presets in Phase 2.

### B2 — The wide-kernel LUT cannot exist

**v0.1 said:** fuse into a 5×5/7×7 kernel (§6a.2) *and* "encode local neighborhood comparisons as
a bit pattern and index into a small, cache-friendly LUT texture" (§6a.3).

**Problem:** these are in direct conflict. HQx's LUT works because a 3×3 neighborhood gives 8
binary comparisons → 2⁸ = 256 entries. A 5×5 neighborhood gives 24 comparisons → 2²⁴ ≈ 16.7M
entries. That is not small and not cache-friendly; at 4 bytes/entry it is ~67 MB.

**Change:** two-level decomposition. The 3×3 binary edge topology keeps a genuine 256-entry LUT
(the HQx-portable part). The wide 5×5/7×7 kernel feeds cheap **scalar statistics** computed in ALU
— local variance, checkerboard autocorrelation, stroke-width estimate, unique-color count — which
select which reconstruction rule the LUT result is applied under. No table, no branching.

**Consequence:** this is now the project's highest-risk technical assumption and gets a dedicated
Phase-0 spike (T-004) before any tier is built on it.

### B3 — Vertex-shader varying offsets exceed the hardware limit

**v0.1 said (§6a.6):** "Precompute sample offsets in the vertex shader and pass them as varyings
where the hardware supports it."

**Problem:** Adreno 6xx-class hardware provides 16 vec4 varyings / 64 components. A 5×5 kernel is
25 vec2 offsets ≈ 13 vec4 — 81% of the entire varying budget for offsets alone, leaving nothing for
anything else. A 7×7 kernel is 49 offsets ≈ 25 vec4, which **exceeds the limit outright**; Freedreno
reports GPU hangs above 16 vec4 on this family. The v0.1 guidance is unusable at exactly the kernel
sizes v0.1 also requires.

The justification is also dated: the dependent-texture-read penalty this avoids is a PowerVR-era
concern, largely absent on the Adreno 6xx/7xx class named as the target. And the definition is
narrower than v0.1 implies — a read is "dependent" when its coordinate derives from a *previously
sampled value*, not merely because it was computed in the fragment shader. Adding a compile-time
constant to an interpolated base coordinate is non-dependent.

**Change:** pass base coordinate + texel size only (2 vec4), compute offsets in the fragment shader
as constant adds, and prefer `textureGather` — 4 texels per instruction, cutting a 25-tap 5×5 to ~9
gathers. Caveat added: `textureGather` is GLES 3.1+, so a 3.0 fallback may be needed depending on
the device floor.

### B4 — `PassFeedback` is the wrong history source

**v0.1 said (FR4):** use "`OriginalHistory`/`PassFeedback`-style semantics" interchangeably.

**Problem:** they are not interchangeable, and the difference is ~36× on the project's own primary
budget metric. `PassFeedback` reads the previous frame's *pass output* at full output resolution
(~8.3 MB/frame at 1080p, ~500 MB/s at 60fps). `OriginalHistory1` reads the previous frame's *core
input* at native resolution (~229 KB/frame at 256×224, ~14 MB/s). For a design that declares
bandwidth the primary constraint, defaulting to the expensive one by accident is a significant miss.

`PassFeedback` is also worse algorithmically here — blending output into its own input accumulates
error across frames and smears small fast-moving sprites, which is the exact ghosting failure FR9's
fast-action profile is trying to avoid. And the spec limits `PassFeedback` to a single frame while
`OriginalHistory#` supports arbitrary depth.

**Change:** FR4 specifies `OriginalHistory1`, used to derive a per-pixel stability signal that
*modulates reconstruction strength*, with no output-to-output feedback path.

## Optimizations

### O1 — Budget output-resolution passes, not total passes

Pass count budgets the wrong resource. At 1080p from a 256×224 source, a native-res RT round trip
costs ~0.2 B/px versus ~8 B/px for an output-res one. A 4-pass chain with three native-res passes is
substantially cheaper than a 2-pass chain with two output-res passes. Tiers are now budgeted by
output-resolution pass count, with total passes as a secondary note.

This also corrects a smaller inconsistency: v0.1's 2-pass tier put "classification+reconstruction"
in pass 1 at native resolution, which contradicts "expand late" — reconstructing at native res
discards the sub-pixel edge placement the technique depends on. Pass 1 now emits a compact
classification + edge-parameter buffer; pass 2 does the expansion.

### O2 — Express the bandwidth budget as a number

"Minimize passes" is not falsifiable and cannot fail a build. Each tier now carries a hard B/px
ceiling (8 / 10 / 32) with the derivation shown, measured rather than estimated. For scale, 32 B/px
at 4K60 is ~16 GB/s against the ~12-17 GB/s of shared LPDDR4X typical of this handheld class —
which is the quantitative reason the desktop tier is not a mobile fallback.

### O3 — `textureGather` as a first-class lever

Absent from v0.1 entirely, despite being the most direct available lever on fetch count for a
multi-tap classifier. Added to §6a.6 with its GLES 3.1 caveat.

## Process and sequencing fixes

### P1 — Cross-backend compile gate moves to Phase 0

v0.1 deferred backend porting to Phase 2. Portability is a hard NFR, and a cross-compilation
failure found after the algorithm is fixed costs far more than one found on a stub pass. Standing
the gate up in Phase 0 is cheap and converts Phase 2 from a porting exercise into runtime
verification.

### P2 — Automated golden-image regression, not perceptual A/B as the primary mechanism

v0.1's validation plan is almost entirely manual (imgsli, blind surveys). That cannot gate a commit
and does not scale across 3 tiers × ~20 presets × N content × 4 backends. A headless deterministic
frame-dump comparator becomes the primary harness; perceptual review becomes a spot-check on
intentional changes.

### P3 — Text negative set must exist before the glyph heuristic is tuned

v0.1 listed false-positive risk as an open question to test later. Tuning class (d) against a
positive-only set optimizes a metric that rewards over-triggering — the heuristic will appear to
succeed *precisely by* misclassifying fur, hair, and thin outlines as text. The negative set has to
gate the classifier from the first tuning pass, so it moves into Phase 0 alongside the positive set.

### P4 — Content corpus must be redistributable

v0.1 called for a curated content set without addressing that a public repo cannot ship captured
frames from commercial ROMs. Corpus is now built from homebrew/public-domain titles plus synthetic
patterns isolating one failure mode each. The synthetic patterns are an improvement on their own
terms — whole-game frames confound several effects, so a regression cannot be attributed to a cause.

### P5 — Licensing resolves in Phase 0, not "eventually"

v0.1 left licensing in Open Questions. It determines whether reference shader source may be
consulted while authoring, so answering it late risks a clean-room determination that invalidates
completed work. It is a precondition for Phase 1, not a question.

### P6 — Nearest-neighbour added as a mandatory baseline

v0.1's comparison set contained only other upscalers. A meaningful share of the audience prefers
unfiltered integer scaling; without it in the set, the study cannot answer whether the shader beats
doing nothing.

### P7 — Numeric exit criteria per phase, and three parallel tracks

v0.1's phases had no measurable completion condition ("validate bandwidth before adding features"
does not say against what). Each phase now carries numeric criteria. Separately, v0.1 implied a
strictly serial plan, but tooling (Track B) and content (Track C) share no code with the shader core
(Track A) and can run alongside — Track C in particular *gates* Phase 1 classifier tuning, so
serializing it behind Phase 1 would stall the critical path.

### P8 — Temporal correctness needs explicit cases

The run-ahead NFR was stated as an assumption. Two concrete hazards need testing: the spec defines
frames at N < 0 as transparent black, so cold start / reset / save-state restore have no valid
history and must not blend against black; and **rewind reverses frame order**, inverting the sign of
any motion signal derived from history. Both are now named test cases gating FR4.
